# Spec 4 — Course Pipeline

*Provides: course state machine (4.2), syllabus + GUIDANCE artifacts consumed by 5/6. Consumes: 2 (gateway, prompts), 3 (path API).*

**Decisions that bind this spec** ([ledger](../02-design.md), index at its head): [D7](../02-design.md) the data model · [D7a](../02-design.md) one open course per subtopic · [D7b](../02-design.md), [D7c](../02-design.md), [D7d](../02-design.md) withdrawal, the two dates, and the one status vocabulary — **read D7d for the current rule** · [D9](../02-design.md) one machine, two ends · [D10](../02-design.md) and [D10.1](../02-design.md)–[D10.5](../02-design.md) the syllabus is rows, and four smaller things 4.5 forced · [D11](../02-design.md) `users.plan` is a string · [D14](../02-design.md) `PendingCall::userTurn()` is interview-only · [D25](../02-design.md) both `top`-tier generations are queued · [D28](../02-design.md) the mounted-component class (4.7) · [D34](../02-design.md) `final_exam_concepts` is emphasis, not scope · [D35](../02-design.md) how 4.7's client-side claim is proven · [D36](../02-design.md) the interview opener is a wire artefact · [D38](../02-design.md) the question budget asks for an ending, never imposes one (supersedes D37) · [R1](../02-design.md) personas are repo prompt files behind `courses.style` · [R3](../02-design.md) interview termination. Trap: [T2](../lessons.md).

State machine (ledger D7, amended by D7c): created → knowledge_interview → goals_interview → syllabus_draft ⇄ syllabus_revision → active → final_exam. No end state — passing the exam stamps `completed_at` (6.3), failing returns the course to `active`. Placement states slot in at v1.1. Exclusivity (ledger D7a, amended by D7b/D7c): at most one course per (user, subtopic) is *open*, where open = `withdrawn_at IS NULL AND completed_at IS NULL`, held by a partial unique index that names no statuses. Withdrawing stamps `withdrawn_at` and keeps the row; `attempt` (scoped to user × subtopic × skill_level) lets a level be taken again. Resuming clears the stamp and restores the student to the status they held; only the highest-numbered attempt is resumable.

**NOTE:** Spec 3.3 is blocked on 4.1 and is built as part of this section.

- **4.1 MUST** — Preset catalog (Math, Science, History, Language, Econ, Philosophy + subtopics) + free-text creation. Two mismatches, two mechanisms: **subtopic against module** blocks at creation (4.9), **goals against subtopic** flags at syllabus time (4.5.7). *Done: both paths create `courses` row in `created`.*
- **4.2 MUST** — State machine as single transition service; workflows fire on transitions; illegal transitions throw. *Done: per-state side-effect tests.*
- **4.3 MUST** — Knowledge interview (streamed; ends per 2.3.4) → `wk.create` → `{module}/{subtopic}/WORKING_KNOWLEDGE.md` (subtopic-scoped, ledger D8). The interview transcript is **kept** once summarized (D9, amended 2026-09-19): nothing deletes a record of a model interaction, and the summary is a derived document rather than a replacement for it. The WK is shared across levels (D8), so `wk.create` takes `prior_wk_doc` — the accumulated document, or an explicit "none yet" on the first course in the subtopic — and the interview revises what is there rather than replacing it (D7a). Landing this updates `wk.create`'s inputs in the 2.3.2 inventory. *Done: WK file with solid/shaky/gaps; a 101→201 progression keeps the 101 document's claims.*
- **4.4 MUST** — Goals interview → `criteria.create` → `COURSE_CRITERIA.md`. *Done: analogous.*

## 4.5 Syllabus generation, review, approval

- **4.5.1 Generation — MUST.** Inputs: WK + CRITERIA + skill-level variant + depth params. Tier top. Strict JSON; 1 retry as a plain re-issue of the same call; then fail-**closed** (user-facing error — nothing downstream exists to protect). Generation performs no transition and writes no row unless it succeeded, so a failure leaves the course exactly where it stood (ledger D10.4). Global rule: *fail open only when failing closed would destroy student progress.* *Done: fixture produces valid syllabus; double-failure shows error path, writes no row and leaves `courses.status` unchanged.*
- **4.5.2 `json/syllabus.v1` — MUST.** `{course_title, overview, lessons[{position, title, objective, sections[{title, concepts[slugs]}], homework_focus, estimated_minutes}], final_exam_concepts[], subtopic_mismatch|null}`. The `concepts` slug vocabulary is the connective tissue: declared here, tagged in checkpoints (5.2.2), reported in summaries (5.4.2), drawn on by exams/refreshers (6.3/6.4). *Done: schema enforced; every downstream slug resolves to a declared slug.*
  - **4.5.2.1 Schema definition — MUST.** The `Closure(JsonSchema)` package 4 hands the gateway; 2.3.1 declares the `json/syllabus.v1` output, the schema itself belongs here. *Done: a prompt declaring this output with no schema throws; a drift test pins both syllabus prompts' `output:` frontmatter to the schema's contract name.*
  - **4.5.2.2 `SyllabusConcepts` — MUST.** Value object over a syllabus document: declares the slug vocabulary, resolves a slug to the lesson that introduces it, rejects an undeclared one (ledger D10.2). The contract 5.2.2/5.4.2/6.3/6.4 consume — there is no concepts table. *Done: a declared slug resolves to its lesson; an undeclared one throws, naming every offender in a batch at once; `final_exam_concepts` is checked against the lesson-declared vocabulary before any row is written.*
- **4.5.3 GUIDANCE.md materialization — MUST.** At approval, each lesson renders `{module}/{subtopic}/{level}/{lesson-slug}/GUIDANCE.md` from JSON via template. **Model-facing only — read by exactly one consumer, the lesson engine (5.1).** User-facing syllabus view renders from the same JSON. Materialization safe because approved syllabus is immutable (revisit if that ever changes). Rendered by a PHP class rather than a Blade template, and the `{lesson-slug}` segment is position-prefixed so two lessons sharing a title cannot share a path (ledger D10.3). *Done: approval writes N files + versions; golden-file template test; CI check (`GuidanceDoorTest`) fails the build if anything under `routes/`, `app/Http/`, `resources/js/` or `resources/views/` names GUIDANCE.md, `LessonGuidance`, `GuidanceDocument` or `guidance_path`.*
- **4.5.4 Review & revision — MUST.** Approve/revise; revise = free-text feedback → regenerate with [prev JSON + feedback + inputs]; cap 3 revisions then approve-or-restart. Drafts are **app state, not memory tree** — rows in `course_syllabi`, not columns on the course row (amended by ledger D10.1). A failed regeneration leaves the course at `syllabus_revision` with the previous draft intact and retryable. *Done: revise loop at service level; the 4th revision request is refused; a failed revision keeps the draft the student already had.* **UI deferred** — this session built the engine only (Colin, 2026-08-24); the review screen belongs to package 7.
  - **4.5.4.1 `course_syllabi` — MUST.** One row per generation: `course_id`, `generation` (1-based; 1 = the first draft, 2..N = revisions), `syllabus_json`, `feedback` (null at generation 1), `wk_version_id` and `criteria_version_id` → `memory_versions`, `approved_at`, timestamps. Two database rules: one row per generation, one approved row per course. The revision cap is *not* among them — it is policy, and D7c is why policy stays out of schema. A failed generation writes no row. *Done: two rows at one generation violate the index; two approved rows violate the other; a row's pinned versions still return the exact documents the call read after WK has been overwritten.*
- **4.5.5 Approval side-effects — MUST.** One transaction: lesson rows (lesson 1 `available`, rest `locked`) → materialization → `approved_at` on the accepted `course_syllabi` row → state `active`. The memory tree is Postgres too (ledger D3a), so materialization is *inside* the transaction rather than merely near it. *Done: mid-transaction kill leaves zero or all effects.*
  - **4.5.5.1 `lessons` + `LessonStatus` — MUST.** `course_id`, `position`, `status`, `guidance_path` — exactly what D7 listed (ledger D10.5). Titles and objectives are read from the approved syllabus JSON, never stored here. `LessonStatus` ships `locked` and `available`; package 5 owns what comes after a lesson is opened. *Done: no lesson column duplicates a syllabus JSON field; one row per position enforced; 4.5.3's door check still passes.*
- **4.5.6 Depth parameters — SHOULD.** `depth = f(skill_level, plan)`, config-keyed `depth.{skill_level}.{plan}`. v1: plan constant; depth varies by skill level on **pedagogical** grounds (101 may be longer than 301). **Skill level ⊥ price** (founder correction). Post-v1 billing attaches to `plan` only. Billing itself **WONT** in v1. *Done: changing plan alone changes depth in fixture.*
  - **4.5.6.1 `users.plan` — SHOULD.** String column, one shipped value, no price, entitlement or branch (ledger D11). An unknown plan surfaces at depth resolution, the only thing in v1 that reads it. *Done: an unknown plan throws; the configured default matches both the schema default and the model default.*
  - **4.5.6.2 `depth_params` rendering — SHOULD.** Config values render into the prompt variable as a markdown key list, matching the house style of `prompts/syllabus/generate.md`. Deliberately not JSON — a structured blob invites the model to echo the structure rather than read it as instruction. *Done: golden-string test over the rendered variable at each skill level.*
- **4.5.7 Mismatch handling — MUST.** Non-null `subtopic_mismatch` → non-blocking banner on review screen. *Done: mismatch fixture approves normally and starts the course; the flag is carried on the syllabus payload the review screen reads.* **Banner deferred** with 4.5.4's UI; the engine half — a mismatch never blocks approval — is built and tested.

## Dogfood repair (2026-09-07)

- **4.3.1 MUST** — The knowledge interview is **budgeted at five questions**, and asks to end rather than ending ([D38](../02-design.md)). At five, `InterviewSession` swaps the brief's `pacing` variable from "ask your next question" to a wrap-up instruction, and keeps it there for every turn after — so the request to finish arrives when it is wanted and repeats instead of decaying under a growing transcript. Nothing forces an ending: [R3](../02-design.md)'s two doors are still the only ones, and a tutor that keeps asking runs long rather than cutting the student off. The number is never stated to the model, only "ask your next question" or "wrap up now". A student who *says in the conversation* that they have had enough is pointed at the Done button rather than talked past: their words do not end an interview, and the brief no longer asks the tutor to keep them going as though they had not spoken. *Done: the fifth question is the one after which the brief asks the tutor to wrap up; a tutor that asks anyway is not cut off — the interview stays open, the request repeats on every turn, and Done still ends it; a student saying they want to stop does not end the interview by saying it; a test drives all three paths.*
- **4.4.1 MUST** — The goals interview is budgeted at four questions, the same way. `prompts/interview/goals.md` names the four in order and asks for `signal_complete` after the fourth answer. **One question per section of `criteria.create`**, so the interview and the document it becomes are the same four things: what the student hopes to gain (goals), what drew them to the subject and the contexts worth building lessons around (interests), what "finished" looks like (success), and how they want to be evaluated (evaluation style). *Done: a goals interview whose tutor wraps up when asked holds exactly four tutor questions, and `criteria.create` still produces goals, interests, success and evaluation preference from them.*
- **4.6 MUST** — The opener is not a student turn. `InterviewSession::OPENING_TURN` exists on the wire and nowhere else: it is never an `interview_messages` row, so no screen paints it and no summarizer reads it. It cannot be removed outright — see 4.6.1 and [D36](../02-design.md). *Done: neither interview shows it; the model still opens the conversation.*
  - **4.6.1 SHOULD** — Establish whether the opener is needed at all before changing how it is stored — removal is a smaller change than hiding. *Done: the finding is [D36](../02-design.md) — it is needed, twice over, so 4.6 is satisfied by unstoring it rather than by removal.*
- **4.7 MUST** — The knowledge → goals transition opens the goals stream without a page refresh. Both screens render `courses/interview`, and the transition is `router.reload()` following a redirect — a state-preserving visit, which leaves the component mounted and its `opened = useRef(false)` guard still true, so the goals stream is never requested. The screen is keyed on `kind`; it may not rely on Inertia to remount it. See [D28](../02-design.md). *Done: completing the knowledge interview lands on the goals interview with the tutor's first question streaming, no error shown and no manual reload; a test asserts the goals stream is requested when the goals props reach the mounted knowledge screen, which is what a state-preserving visit delivers.*
- **4.8 MUST** — A syllabus is stored as prose, not as JSON source. One `syllabus.generate` call escaped its own strings a second time and wrote `\u2014` and `\n\n` where an em dash and a paragraph break belonged; the syllabus screen, the lesson completion screen and the GUIDANCE document the tutor reads back all printed what they were given. `SyllabusGenerator` decodes a string on the way in, and only when the whole of it reads as a JSON string body — a stray backslash repairs nothing rather than something. Both doors go through it, so a revision is covered too. See [D39](../02-design.md). *Done: a scripted generation carrying `\u2013` and `\n\n` is stored with the dash and the break; a string that is not a whole JSON body is stored exactly as the model wrote it.*
- **4.9 MUST** — A free-text subtopic is checked against its module **before any row is written**. "algebra" typed under Language started a Language course about algebra and carried it through the interview, the working knowledge document and the syllabus; so did "medieval history" and "physics". 4.1 deferred mismatch to 4.5.7, but that flag is *goals against subtopic*, raised by `syllabus.generate` after two interviews and a `top`-tier call — nothing had ever asked whether the subtopic belonged to the module. Mismatch stays a flag at syllabus time and becomes a blocker at creation time; see [D42](../02-design.md). *Done: a free-text name that does not belong to its module writes no `courses` row and starts no interview; the catalog path is unchanged and calls no model.*
  - **4.9.1 MUST** — The gate spends nothing it need not. `UnusableSubtopicName` still refuses a blank, unsluggable or over-length name with no call. A name whose slug matches a **listed** subtopic **in the chosen module** is in scope with no call; an unlisted student subtopic ([16.1](16-catalog-removal-ownership.md)) passed the check once, for someone else, and is checked again — `SubtopicName` already makes "spanish" under Language the catalog's Spanish. *Done: a blank name and a name matching a same-module preset both complete with zero `usage_events` rows.*
  - **4.9.2 MUST** — `subtopic.check`, tier `cheap`, vars `catalog`, `module`, `name`, `collision`. The catalog renders from `modules` and the **listed** `subtopics` rows rather than from the prompt file, because promotion ([16.1.5](16-catalog-removal-ownership.md)) adds to them. `collision` renders **only** when the typed slug matches a listed subtopic under a *different* module, and says the match does not settle the question: without it the model reads the catalog as an ownership table and refuses `logic` under Math because Philosophy lists it. Landing this adds the row to the 2.3.2 inventory. *Done: the inventory audit and the render fixture pass; a rendered prompt with no collision carries no collision sentence, asserted directly since the 1:1 fixture pins only one of the two shapes.*
  - **4.9.3 MUST** — `json/subtopic-scope.v1` — `{verdict: in_scope|wrong_module|off_platform, module: <module slug>|null, reason}`. `module` is enum-constrained to seeded module slugs and is non-null only for `wrong_module`. The schema is defined inside the checking service rather than in a class of its own: unlike `json/quiz.v1` it has one consumer and always will. *Done: a verdict naming an unseeded module is rejected; `wrong_module` with a null module is rejected.*
  - **4.9.4 MUST** — The check runs **before** D7b's "carry on, or start over?" question, so a misfiled name never raises a resume prompt about a course that should not exist. Its two refusals are exceptions caught in `store()` beside the two already there: `SubtopicBelongsElsewhere`, carrying the target module, and `SubtopicOutOfScope`. *Done: a withdrawn attempt at a misfiled name shows the scope refusal rather than the resume question; neither refusal writes a `courses` row.*
  - **4.9.5 MUST** — A check that cannot run **fails closed**: one retry, a 15-second budget per attempt, then no course and an inline error on the picker. This is 4.5.1's rule as written rather than an exception to it — nothing downstream exists to protect. Degraded mode is explicit: during a provider outage the catalog path still starts any preset subtopic, because it calls no model. *Done: a provider that throws twice writes no `courses` row and returns the student to the picker with name, module and level intact; a provider that throws once and then answers starts the course.*
  - **4.9.6 MUST** — The student reads **our** words, never the model's. Copy is generated from the verdict and the two module titles; a probe had the model call business writing an Economics subject three times out of three, in a fluent sentence a student would believe. Three messages, the third distinct because "try again" means something else when the check never ran: *"«Algebra» isn't a Language topic. It's one we teach under Math."* · *"We can't build a course around «how to fix my carburetor.»"* · *"We couldn't check that topic just now."* The first two carry *"If you believe this is a mistake, please try again"*; the outage message does not, because it already says so. The wrong-module screen offers **Start Algebra under Math** and **Pick something else**, and no override — the refusal means something or it means nothing. S2 is 8.7.1's screen and this work stays here regardless: one owner, one commit, with 8.7 holding a pointer. *Done: the model's `reason` appears in no rendered output; the offered module button starts the same subtopic under the named module in one submission, carrying the level.*
  - **4.9.7 MUST** — `subtopic_refusals`, one row per refusal: student, typed name, chosen module, verdict, suggested module, the model's `reason`. The reason is stored and never rendered to a student; Admin → Catalog → Refusals ([16.1.6](16-catalog-removal-ownership.md)) reads it back. *Done: a `wrong_module` and an `off_platform` refusal each leave one row carrying the reason; an `in_scope` verdict leaves none.*
  - **4.9.8 MUST** — Four documents this makes false are repaired in the same commit: `CourseCatalogSeeder`'s "free text creates any subtopic under any module"; `prompts/syllabus/generate.md`'s "note any mismatch rather than refusing", which stays true for goals against subtopic and must now say which mismatch it means; `CourseController`'s docblock, which names two refusals and will have four; and 4.1's "mismatch handled at 4.5.7", which now names two mechanisms. *Done: none of the four asserts something the code no longer does.*
  - **4.9.9 WONT** — A support channel or contact line; a feedback form; an override that starts a course under a module the check rejected; any change to 4.5.7's non-blocking goals mismatch; a catalog admin UI.


## Acceptance test

*The journey this package's items compose into. The per-item done-conditions each prove one item; this proves they work together (ledger [D29](../02-design.md)). It is runnable without opening another spec.*

As a signed-in student with no open course in the subtopic:

1. Create a course from the catalog at 101, and a second from free text in another subtopic. Both exist as rows; a third attempt at either subtopic while it is open is refused.
2. Answer the knowledge interview. It closes itself at the fifth question with the tutor saying that is enough — and asking to stop at question three does not end it, while the always-visible Done button does, at any point. The transcript is summarized into working knowledge, folded into whatever was there before.
3. Answer the goals interview. Exactly four tutor questions, the first two being what the student hopes to gain and what drew them to the subject; the transcript becomes the criteria document for this level. Arriving here from the knowledge interview needs no page refresh.
4. Ask for a syllabus. The request returns immediately and the screen waits on the generation; the draft that arrives declares five to ten lessons, each with an objective, sections, concepts and a homework focus, pinned to the versions of working knowledge and criteria it was written from. Every line of it reads as prose — no escape sequence stands where a dash or a paragraph break belongs. Press twice — the second press costs nothing.
5. Send free-text feedback and get a new draft. Do it three times and the fourth offer is approve-or-restart. A generation that fails leaves the previous draft standing and says so.
6. Approve. In one transaction the lesson rows appear with the first unlocked and the rest locked, a guidance document is rendered for each, the draft is stamped approved and the course is active.
7. Set the course aside, then take it back up: it returns at the position it left. Withdraw it and create the subtopic again — attempt 2, with attempt 1's working knowledge intact.
