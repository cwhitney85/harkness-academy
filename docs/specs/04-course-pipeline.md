# Spec 4 — Course Pipeline

*Provides: course state machine (4.2), syllabus + GUIDANCE artifacts consumed by 5/6. Consumes: 2 (gateway, prompts), 3 (path API). See PLAN.md for status.*

State machine (ledger D7, amended by D7c): created → knowledge_interview → goals_interview → syllabus_draft ⇄ syllabus_revision → active → final_exam. No end state — passing the exam stamps `completed_at` (6.3), failing returns the course to `active`. Placement states slot in at v1.1. Exclusivity (ledger D7a, amended by D7b/D7c): at most one course per (user, subtopic) is *open*, where open = `withdrawn_at IS NULL AND completed_at IS NULL`, held by a partial unique index that names no statuses. Withdrawing stamps `withdrawn_at` and keeps the row; `attempt` (scoped to user × subtopic × skill_level) lets a level be taken again. Resuming clears the stamp and restores the student to the status they held; only the highest-numbered attempt is resumable.

## 4.5 Syllabus generation, review, approval

- **4.5.1 Generation — MUST.** Inputs: WK + CRITERIA + skill-level variant + depth params. Tier top. Strict JSON; 1 retry as a plain re-issue of the same call; then fail-**closed** (user-facing error — nothing downstream exists to protect). Generation performs no transition and writes no row unless it succeeded, so a failure leaves the course exactly where it stood (ledger D10.4). Global rule: *fail open only when failing closed would destroy student progress.* *Done: fixture produces valid syllabus; double-failure shows error path, writes no row and leaves `courses.status` unchanged.*
- **4.5.2 `json/syllabus.v1` — MUST.** `{course_title, overview, lessons[{position, title, objective, sections[{title, concepts[slugs]}], homework_focus, estimated_minutes}], final_exam_concepts[], subtopic_mismatch|null}`. The `concepts` slug vocabulary is the connective tissue: declared here, tagged in checkpoints (5.2.2), reported in summaries (5.4.2), drawn on by exams/refreshers (6.3/6.4). *Done: schema enforced; every downstream slug resolves to a declared slug.*
  - **4.5.2.1 Schema definition — MUST.** The `Closure(JsonSchema)` package 4 hands the gateway; 2.3.1 declares the `json/syllabus.v1` output, the schema itself belongs here. *Done: a prompt declaring this output with no schema throws; a drift test pins both syllabus prompts' `output:` frontmatter to the schema's contract name.*
  - **4.5.2.2 `SyllabusConcepts` — MUST.** Value object over a syllabus document: declares the slug vocabulary, resolves a slug to the lesson that introduces it, rejects an undeclared one (ledger D10.2). The contract 5.2.2/5.4.2/6.3/6.4 consume — there is no concepts table. *Done: a declared slug resolves to its lesson; an undeclared one throws, naming every offender in a batch at once; `final_exam_concepts` is checked against the lesson-declared vocabulary before any row is written.*
- **4.5.3 GUIDANCE.md materialization — MUST.** At approval, each lesson renders `{module}/{subtopic}/{level}/{lesson-slug}/GUIDANCE.md` from JSON via template. **Model-facing only — read by exactly one consumer, the lesson engine (5.1).** User-facing syllabus view renders from the same JSON. Materialization safe because approved syllabus is immutable (revisit if that ever changes). Rendered by a PHP class rather than a Blade template, and the `{lesson-slug}` segment is position-prefixed so two lessons sharing a title cannot share a path (ledger D10.3). *Done: approval writes N files + versions; golden-file template test; CI check (`GuidanceDoorTest`) fails the build if anything under `routes/`, `app/Http/`, `resources/js/` or `resources/views/` names GUIDANCE.md, `LessonGuidance`, `GuidanceDocument` or `guidance_path`.*
- **4.5.4 Review & revision — MUST.** Approve/revise; revise = free-text feedback → regenerate with [prev JSON + feedback + inputs]; cap 3 revisions then approve-or-restart. Drafts are **app state, not memory tree** — rows in `course_syllabi`, not columns on the course row (amended by ledger D10.1). A failed regeneration leaves the course at `syllabus_revision` with the previous draft intact and retryable. *Done: revise loop at service level; the 4th revision request is refused; a failed revision keeps the draft the student already had.* **UI deferred** — this session built the engine only (Colin, 2026-08-24); the review screen belongs to package 7.
  - **4.5.4.1 `course_syllabi` — MUST.** One row per generation: `course_id`, `generation` (1-based; 1 = the first draft, 2..N = revisions), `syllabus_json`, `feedback` (null at generation 1), `wk_version_id` and `criteria_version_id` → `memory_versions`, `approved_at`, timestamps. Two database rules: one row per generation, one approved row per course. The revision cap is *not* among them — it is policy, and D7c is why policy stays out of schema. A failed generation writes no row. *Done: two rows at one generation violate the index; two approved rows violate the other; a row's pinned versions still return the exact documents the call read after WK has been overwritten.*
- **4.5.5 Approval side-effects — MUST.** One transaction: lesson rows (lesson 1 `available`, rest `locked`) → materialization → `approved_at` on the accepted `course_syllabi` row → state `active`. The memory tree is Postgres too (ledger D3a), so materialization is *inside* the transaction rather than merely near it. *Done: mid-transaction kill leaves zero or all effects.*
  - **4.5.5.1 `lessons` + `LessonStatus` — MUST.** `course_id`, `position`, `status`, `guidance_path` — exactly what D7 listed (ledger D10.5). Titles and objectives are read from the approved syllabus JSON, never stored here. `LessonStatus` ships `locked` and `available`; package 5 owns what comes after a lesson is opened. *Done: no lesson column duplicates a syllabus JSON field; one row per position enforced; 4.5.3's door check still passes.*
- **4.5.6 Depth parameters — SHOULD.** `depth = f(skill_level, plan)`, config-keyed `depth.{skill_level}.{plan}`. v1: plan constant; depth varies by skill level on **pedagogical** grounds (101 may be longer than 301). **Skill level ⊥ price** (founder correction). Post-v1 billing attaches to `plan` only. Billing itself **WONT** in v1. *Done: changing plan alone changes depth in fixture.*
  - **4.5.6.1 `users.plan` — SHOULD.** String column, one shipped value, no price, entitlement or branch (ledger D11). An unknown plan surfaces at depth resolution, the only thing in v1 that reads it. *Done: an unknown plan throws; the configured default matches both the schema default and the model default.*
  - **4.5.6.2 `depth_params` rendering — SHOULD.** Config values render into the prompt variable as a markdown key list, matching the house style of `prompts/syllabus/generate.md`. Deliberately not JSON — a structured blob invites the model to echo the structure rather than read it as instruction. *Done: golden-string test over the rendered variable at each skill level.*
- **4.5.7 Mismatch handling — MUST.** Non-null `subtopic_mismatch` → non-blocking banner on review screen. *Done: mismatch fixture approves normally and starts the course; the flag is carried on the syllabus payload the review screen reads.* **Banner deferred** with 4.5.4's UI; the engine half — a mismatch never blocks approval — is built and tested.
